# 🎬 Filmin — Talent Meets Cinema (MVP v1.0)

> An interview-ready, full-stack talent platform connecting film and entertainment professionals with casting calls and crew requirements.

---

## 📌 Executive Summary

Filmin is a structured talent and production discovery platform designed for the indie and mainstream film ecosystem. It replaces scattered WhatsApp groups and social media casting calls with a verified, secure workflow:

**Core Product Loop:**
`Register` ➔ `Build Verified Profile` ➔ `Publish Opportunity` ➔ `Search & Filter` ➔ `Apply with Reel` ➔ `Review Applicants` ➔ `Update Status`

---

## 🏗️ Technical Architecture

Filmin is built as a **Modular Monolith** designed for high auditability, relational data integrity, and strict access controls.

```
Browser (React 18 + TS + Tailwind)
        │
        ▼ HTTPS + REST JSON (Cookie Session / Bearer)
   API Gateway / Modular Controllers
   ├── Auth Module (/api/auth)
   ├── Profile Module (/api/profiles)
   ├── Opportunity Module (/api/opportunities)
   └── Application Module (/api/applications)
        │
        ▼ Service Layer (Business Rules & IDOR Ownership Checks)
        │
        ▼ Persistence / Repositories
        │
        ▼ Relational Storage (PostgreSQL / Flyway Migrations)
          - UNIQUE(opportunity_id, applicant_id)
          - Strict Foreign Keys & Indexes
```

### Stack Breakdown

| Layer | Technology | Key Architectural Rationale |
|---|---|---|
| **Frontend** | React 18, TypeScript, Vite, Tailwind CSS | Type-safe UI, responsive mobile/desktop layouts, cinematic aesthetic |
| **Backend (Primary)** | Java 17, Spring Boot 3.2, Spring Security, JPA | Mature enterprise ecosystem, modular packages, strict validation |
| **Backend (Companion)** | Node.js, Express, TypeScript | Instant 1-command local execution without pre-installed DBs |
| **Persistence** | PostgreSQL (Prod) / Flyway Migrations | Relational integrity, transactional guarantees, race-condition constraints |
| **Security** | BCrypt, Session Cookies, Ownership Filters | IDOR defense, no entity exposure (DTO pattern), CSRF defense |

## 🗄️ Relational Schema & Constraints

```sql
-- Enforced via Flyway V1__init_schema.sql

CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    account_status VARCHAR(50) NOT NULL DEFAULT 'ACTIVE',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE profiles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE REFERENCES users(id) ON DELETE RESTRICT,
    display_name VARCHAR(150) NOT NULL,
    primary_role VARCHAR(100) NOT NULL,
    skills TEXT,
    location VARCHAR(150),
    bio TEXT,
    experience_years INTEGER NOT NULL DEFAULT 0 CHECK (experience_years >= 0),
    portfolio_links TEXT,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE opportunities (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    creator_id BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    title VARCHAR(255) NOT NULL,
    opportunity_type VARCHAR(50) NOT NULL,
    role_needed VARCHAR(100) NOT NULL,
    description TEXT NOT NULL,
    location VARCHAR(150) NOT NULL,
    deadline DATE NOT NULL,
    status VARCHAR(50) NOT NULL DEFAULT 'OPEN',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE applications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    opportunity_id BIGINT NOT NULL REFERENCES opportunities(id) ON DELETE RESTRICT,
    applicant_id BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    cover_message TEXT,
    status VARCHAR(50) NOT NULL DEFAULT 'SUBMITTED',
    submitted_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    -- CRITICAL CONCURRENCY INVARIANT:
    CONSTRAINT uk_application_opportunity_applicant UNIQUE (opportunity_id, applicant_id)
);
```

## 💼 System Design & Interview Q&A (PRD Section 16)

### Q1. Why choose a Modular Monolith instead of Microservices?
> For the MVP stage, domain boundaries (Auth, Profile, Opportunity, Application) are tightly coupled within one transactional context. A modular monolith provides single-unit deployments, zero network latency between services, simplified local debugging, and shared relational transactions. Boundaries can be split into separate microservices later if scaling demands it.

### Q2. Why PostgreSQL with Flyway?
> Film recruiting requires strict relational guarantees: foreign keys from applications to opportunities and applicants, transactions when changing application statuses, and unique constraints to prevent race-condition duplicate applications. Flyway guarantees reproducible, version-controlled schema upgrades across dev, test, and production.

### Q3. How do you prevent Insecure Direct Object References (IDOR)?
> Every mutating request extracts the authenticated user ID from the server-managed session/token—never trust user IDs in the request body. Before updating an opportunity or reviewing applicants, the service explicitly checks `opportunity.getCreator().getId().equals(currentUserId)` and throws `403 Forbidden` if unauthorized.

### Q4. How do you prevent duplicate applications during concurrent submissions?
> A check like `if (repo.exists(...))` is subject to time-of-check to time-of-use (TOCTOU) race conditions when two requests arrive simultaneously. Filmin enforces the invariant at the database level using `CONSTRAINT uk_application_opportunity_applicant UNIQUE (opportunity_id, applicant_id)`. Any race condition is caught by the database and translated to `409 Conflict`.

### Q5. Why use DTOs instead of exposing JPA Entities?
> Exposing JPA entities directly risks mass-assignment vulnerabilities (e.g., an applicant sending `creatorId` or `status: ACCEPTED` in the payload) and accidentally leaking sensitive fields such as password hashes. DTOs form an explicit, validated contract between client and server.

## 🚢 Production Deployment Architecture

- **Frontend:** Hosted on **Vercel** with HTTPS and automatic build triggers.
- **Backend:** Hosted on **Render** (via included `backend/Dockerfile`).
- **Database:** Hosted on **Neon Serverless PostgreSQL** with Flyway migrations.

### Environment Variables
```env
SPRING_PROFILES_ACTIVE=prod
DATABASE_URL=jdbc:postgresql://<neon-host>:5432/<dbname>?sslmode=require
DATABASE_USERNAME=<neon-user>
DATABASE_PASSWORD=<neon-password>
FRONTEND_ORIGIN=https://filmin.vercel.app
SESSION_COOKIE_SECURE=true
```
